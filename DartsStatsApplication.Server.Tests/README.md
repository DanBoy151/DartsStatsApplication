# DartsStatsApplication.Server.Tests

Unit test project for the server, covering the `Services/Validators` business-rule layer plus the
pure, session-free calculators under `Services/` (stats, form/trend, season status, dart-score legality).

## What's covered

- `GameControllerValidatorTests.cs` — `GameControllerValidator.ValidateSelectedPlayers()`: required player count per game type (Singles 1 / Doubles 2 / Trebles 3), and that the roster can still be changed while `Ready` but not once `InProgress`/`Complete`.
- `GameCompletionValidatorTests.cs` — `GameControllerValidator.IsValidToStartGame()`, `IsValidToCompleteGame(List<Leg>, CompleteGameData)`, and `IsValidToCreateNextLeg(int existingLegCount)`: status guards, majority-decided-early completion (computed from the game's configured `legsToPlay`, not just how many Leg documents happen to exist yet), result-vs-leg-majority consistency, and refusing another Leg once `legsToPlay` is already reached.
- `LegControllerValidatorTests.cs` — `LegControllerValidator.IsValidToCompleteLeg()` and `IsValidToCompleteLegByBullOff()`: leg-status guard, required result, win/loss score reconciliation against the starting score, the 1–3 finish-darts rule, that every visit is a score achievable with real darts (`DartScoring`), that a checkout visit can actually end on a double, and the bull-off path only being available once the configured `maxRounds` has genuinely been passed.
- `DartScoringTests.cs` — `DartScoring.IsValidDartScore()`/`IsValidCheckoutScore()`: the 9 scores no combination of real darts can produce (163/166/169/172/173/175/176/178/179), the 4 scores that are reachable but can't end on a double (159/162/165/168), the max checkout (170), and that 180 is a valid score but not a valid checkout.
- `MatchControllerValidatorTests.cs` —
  - `IsValidToCompleteMatch(List<Game>)`: all-games-complete, player-of-the-match participation, and a regression guard for the aggregation bug where the games check used to be overwritten by the player check.
  - `ValidateNewMatch(MatchData)`: opponent required/max length, date required, and that a newly created match must be `Scheduled`.
  - `ValidateEditMatch(Match, MatchData)`: only a Scheduled match is editable, plus the same opponent/date checks as create.
  - `ValidateCanDeleteMatch(Match)`: only a Scheduled match can be deleted.
- `PlayerControllerValidatorTests.cs` — `PlayerControllerValidator.ValidateName(PlayerData)` (shared by create and rename): name required (including whitespace-only), max length, and that surrounding whitespace doesn't itself fail validation (trimming happens in the controller, after validation).
- `LeagueControllerValidatorTests.cs` — league ruleset validation: name required/max length, at least one of Singles/Doubles/Trebles configured (the other two may be zero), legs-per-game and starting scores must be at least 1, and `maxRounds` (when set) must be at least 1.
- `TeamControllerValidatorTests.cs` — team name required/max length (at, and one over, the limit).
- `SeasonControllerValidatorTests.cs` — new-season validation: name required/max length, and that a League and Team must actually be selected.
- `SeasonStatusCalculatorTests.cs` — `SeasonStatusCalculator.Calculate(List<MatchStatus>)`: no linked matches or any non-Completed match → `Active`; every linked match `Completed` → `Closed`.
- `PlayerStatsCalculatorTests.cs` — `PlayerStatsCalculator.Calculate(players, legs)`: zeroed/null stats for a player with no legs, average/first-9/highest-checkout math for a won leg, that a lost leg still counts every visit at 3 darts, that a shared Doubles/Trebles leg credits the best-leg dart count to every player on the winning side but the checkout only to whoever actually threw it, that `Pending` legs are ignored while `Started` (in-progress) legs still count toward averages, first-9 using only each leg's first 3 visits across multiple legs, best-leg-darts picking the fewest across multiple wins, a bull-off win counting for the record/average but excluded from checkout/best-leg stats, and results being ordered by 3-dart average descending.
- `PlayerFormCalculatorTests.cs` — `PlayerFormCalculator.DetermineTrend(recentAverage, careerAverage)`: `Unknown` when either average is null, `Increasing`/`Decreasing` once the gap clearly exceeds the ±0.5 threshold, and the exact `+0.5`/`-0.5`/`0` boundary cases resolving to `Steady`.

All of the above are unit-testable with a `null` session because the rules were written as pure functions over in-memory data — where a rule needs related records (a game's legs, a match's games), or an existing document (the match being edited/deleted), the caller loads it and passes it in. `ValidateNewMatch`, `ValidateEditMatch`, `ValidateCanDeleteMatch`, `ValidateName`, and every `*Calculator`/`DartScoring` method are `static` for the same reason: no session involved at all.

## What's still intentionally not covered

- `MatchControllerValidator.IsValidToStartMatch()` and `ValidateAvailablePlayers()`, and `PlayerControllerValidator.ValidateCanDeletePlayer()`, query `_documentSession` directly, so testing them properly needs a real Marten/Postgres-backed session (e.g. via Testcontainers). Deferred until/unless database-backed integration tests are added. (The end-to-end flows they guard - starting a match, setting its roster, deleting a player - are covered instead by the Playwright suite in `e2e/`, which runs against a real Postgres.)
- Likewise, `MatchService.CompleteMatch()`, `GameService.CompleteGame()`/`CreateNextLeg()`, and the `PlayerController`/`TeamController` stats/seasons/form endpoints all load related documents via a direct `_documentSession.Query(...)` before handing off to their (separately unit-tested) pure validators/calculators - so the loading and joining itself needs a real session too, and is covered by `e2e/` instead. This is also where the "Marten 9 requires async data access" bug class has repeatedly shown up (`MatchController.GetNextMatch`, `MatchControllerValidator.IsValidToStartMatch`/`ValidateAvailablePlayers`, `MatchService.CompleteMatch`, `GameService.CompleteGame` - see `e2e/BUGS.md`): a synchronous `.ToList()`/`.FirstOrDefault()` directly on a Marten `IQueryable` compiles fine but throws `NotSupportedException` at runtime, and nothing in this project catches that class of mistake before it reaches a real database. Worth keeping an eye out for the same pattern in any new session-querying code.
